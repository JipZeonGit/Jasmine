# 逻辑删除 (Logical Deletion) 的隐患与架构级优化方案

本文档记录了关于项目中广泛使用的“逻辑删除（如 `deleted = 1`）”机制随着系统长期演进可能诱发的问题，以及针对这些问题的业界成熟化解之道。

---

## 一、 为什么无休止的逻辑删除会成为数据库负担？

当系统在几年时间里积累到几百万级的数据量时，其中可能有 70% 的行都是 `deleted = 1` 的逻辑软删脏数据。系统层面会遭受以下三种主要的压力：

1. **拖累检索性能（全表查毒）**
   哪怕在 ORM（如 MyBatis-Plus）层面自动为你所有的 Query 拼接了 `WHERE deleted = 0` 的条件，但在没有索引辅助或索引失效的情况下，MySQL 做检索依旧要老老实实把所有所谓的“僵尸数据”扫描一遍之后才能过滤掉它。这徒增了大量的 IO。

2. **侵占宝贵的内存资源 (Buffer Pool 污染)**
   被逻辑删除的行依然扎实地存在于 InnoDB 的 B+ 树叶子节点中。MySQL 读取数据页时会将无关死数据一同加载到极度珍贵的 Buffer Pool 核心内存中，挤占真正高频访问的活跃数据，导致“冷数据污染内存”，缓存命中率直线下跌。

3. **引发灾难级的“唯一索引 (Unique Key)”冲突**
   如果针对如 `username` 或 `flower_name` 设置了数据库级别的唯一索引，当你逻辑删除了叫「向日葵」的花之后，再想新增一盆也叫「向日葵」的花时，系统将会抛出 Duplicate Key Error，因为死掉的那盆向日葵仍旧死死咬住了索引坑位。

---

## 二、 企图用“加索引”来解决问题的真相

**纯靠对 `deleted` 加单列索引毫无作用，甚至是负优化。**
因为 `deleted` 仅包含 `0` 和 `1` 两个值，这就意味着它的区分度（Cardinality，基数）极低。MySQL 优化器对极低基数的情况常常会直接判定“查这颗矮胖索引树还不如直接全表扫描划算”，因此单列索引不仅会失效，其建立还占用额外硬盘空前。

**正确姿势：必须依赖“联合索引 (Composite Index)”**
遇到按照某个分类提取信息（如按类别查未删除的花），你必须设立把常查条件放在左侧的联合索引：
`INDEX idx_category_deleted (category_id, deleted)`。
在有了联合索引指路的情况下，数据库能在拿到具体的 `category_id` 时顺便过滤抛弃死数据。

---

## 三、 终极解决方案（业界最佳实践）

虽然适当的联合索引可以续命，但若是你的业务终有一天要飞跃甚至累积几十上百万体量的脏数据，唯有以下两种重武器方案彻底拔除毒瘤：

### 方案 A：冷热数据分离 / 深夜归档（王道作法）
既然数据已被打回冷宫标记为“死”，那它就彻底没资格挤占在线核心库的内存与查询。
通过开启 Spring `@Scheduled` 或使用中间件定一个离线定时任务（如凌晨 3 点）：
1. 找出所有 `deleted = 1` 并且 `update_time` 远超 3 个月以上不活跃的死数据。
2. 将这些数据批量投放到平行的归档库或历史存档归档表（如 `flower_archive`）中以备审计之需。
3. 从主表发送真刀真枪的物理 `DELETE` 将其抹除。
**结果**：主表的树规模永远维持在轻盈的量级，极速运行。

### 方案 B：解决唯一索引的黑科技：使用时间戳代替布尔值
专门对付唯一键冲突问题。不要再将 `deleted` 限制于 `0` 或 `1`（Boolean 类型）：
- 保持存活时：`deleted = 0`。
- 被执行软删时：将 `deleted` 设为 **被删那操作发生的绝对具体时间戳 (如 `1691234567`)** 或主键 ID。
然后把原先的单个约束扩容成联合约束 `UNIQUE KEY (name, deleted)`。
**结果**：哪怕软删了一万盆「向日葵」，每一盆由于死期时间戳全不相同，因此不会跟当下 `deleted=0` 活着的那条产生唯一的排他性冲突。完美逃课！

# PR11 之后的新版路线（草稿）

## 说明

本文档用于承接 `PR11` 完成之后的后续演进路线。

这份草稿的目标不是推翻既有升级主线，而是在 `PR11` 已完成的前提下，把后续几轮工作的重点、顺序和边界重新收口，避免把模块化重组、Redis、RabbitMQ、前端迁移、部署整理混成一团。

当前判断基线如下：

- `PR11` 已经完成核心业务模型重构
- 当前系统已经不再适合继续维持全局 `controller / service / mapper / entity` 平铺组织
- Redis 当前使用较浅，但问题主要在“用得不够准”，不是“必须覆盖全部业务”
- RabbitMQ 可以继续进入路线，但不应该在边界混乱的情况下硬接

## PR12 模块化单体 + 轻量目录规范

### 目标

按业务域重组后端结构，把当前“全局技术分层平铺”的代码组织改造成“先按业务域聚合、再在域内分层”的模块化单体。

同时顺手完成一轮低风险、高收益的目录规范整理，把前端目录从模板残留命名收口成正式项目结构。

### 内容

#### 1. 按业务域拆分后端代码

建议拆成这些域：

- `iam`
- `flower`
- `inventory`
- `sales`
- `vip`
- `appointment`

#### 2. 每个业务域内部再分层

建议统一成：

- `web`
- `application`
- `persistence`
- `model`

#### 3. 公共技术能力收口

把真正公共的能力整理到明确位置：

- `common`
- `config`
- `infra`
- `manager`

建议职责如下：

- `common`：全局通用工具、基础对象
- `config`：框架配置
- `infra`：Redis、JWT、外部集成等基础设施能力
- `manager`：跨域但偏技术协调的逻辑

#### 4. 清理跨域直接依赖

这一轮要尽量避免：

- `sales` 直接注入 `inventory` 的底层 `mapper`
- `appointment` 跳过服务层直接访问 `vip` 的持久层
- 控制器直接编排复杂业务流程

原则是：

- 控制器只做请求接收和响应返回
- 持久层只服务本域
- 跨域调用优先走对方 `application` 层

#### 5. 统一命名和职责边界

这轮顺手统一这些对象的命名和落位：

- DTO / VO / Query / Command
- Service 接口和实现
- Entity / DO / PO 的职责
- Mapper / Repository 的归属

#### 6. 轻量目录规范整理

当前前端目录 `admin` 模板残留痕迹过重，这轮可以顺手改成：

- `admin`

并同步收口这些引用：

- 前端 `package.json` 的 `name`
- README 启动路径
- CI / 脚本里的旧目录路径
- 文档里的旧目录引用

### 说明

- 这一轮以结构重组和目录规范为主，不主打新增业务能力
- 这一轮不做仓库级大搬家，不把后端整体挪进 `backend/`
- 这一轮不重写前端页面，只做前端目录去模板化
- `PR11` 已经把业务模型立住，`PR12` 正好把代码结构和目录结构定下来
- 这是后面做 Redis 收口、RabbitMQ 接入、新前端迁移的必要前置

## PR12.5 Redis 收口

### 目标

把 Redis 从“边缘提速器”提升成“可控的应用层基础设施”，先解决明显一致性问题，再明确适用边界。

### 内容

- 排查并修复缓存一致性问题
- 补齐 `menuList`、权限相关缓存的失效逻辑
- 明确适合缓存的对象：
  - 菜单树
  - 角色列表
  - 花卉主数据列表
  - 少量系统配置或字典类数据
- 明确暂时不缓存的对象：
  - 销售单
  - 销售明细
  - 库存流水
  - 预约创建结果
- 为后续幂等键、分布式锁预留接入位，但不在本轮把 Redis 强行铺到全部业务层

### 说明

- Redis 不需要机械覆盖全部业务层
- 这轮重点是“用对、用稳、边界清楚”
- 做完后再引入 RabbitMQ，会少很多返工

## PR13 RabbitMQ 接入

### 目标

满足“必须学 MQ”的目标，并且不是只做演示性质的接入。

### 内容

- `Spring AMQP`
- `RabbitMQ`
- 生产者 / 消费者基础能力
- 重试 / 死信 / 幂等第一版
- 为 MQ 消费幂等补最小 Redis 支撑：
  - 统一 Redis key 命名约定
  - 消费幂等 key 的基础写法
  - 轻量的 Redis 操作收口门面
- 如果届时项目里出现明确的系统配置或字典读模型，可顺手纳入缓存，但不把这件事单独扩成一轮
- 优先落地场景：
  - 预约通知异步化
  - 审计日志异步化
  - 销售 / 库存事件发布
- 补齐交换机、队列、路由键命名规范

### 说明

- 先从异步通知和事件驱动入手
- 不建议一开始就把核心强一致事务强行改成全异步
- 这一轮只补“对 MQ 直接有帮助”的轻量 Redis 能力，不提前上分布式锁和高并发库存治理
- 真正高并发削峰场景，放到更后面一轮处理

## PR14 Docker / Ops / 部署整理

### 目标

把后端、中间件和运行环境整理成可复现、可联调、可部署的稳定基线。

### 内容

- `ops/`
- 分环境 `compose`
- `ops/.env.example`
- MySQL / Redis / RabbitMQ 联调环境
- 初始化脚本
- 部署文档
- 回滚说明

### 说明

- 当前开发主链仍然以本地非 Docker 环境加 GitHub Actions 容器测试为主
- 这一轮没有必要前移到 `PR13` 之前
- 等 `RabbitMQ` 接入完成、运行环境更稳定后，再集中整理 `Docker / Ops` 更合适

- 后续前端工作以 `web/` 持续迭代为主，不再保留旧前端并行入口
## PR18 高并发与一致性增强

### 目标

在业务模型、模块化单体、Redis、MQ 都基本稳定后，再系统性补高并发防线与最终一致性能力。

### 内容

- 业务提交防重与 Redis 幂等键体系
- Redis 分布式锁或 Redisson
- 热点库存防重 / 防超卖第一版
- 秒杀 / 预扣减 / 热点库存专项方案（仅在后续真实出现高热点抢购场景时启用）
- 基于事件的最终一致性补偿
- Outbox / 本地消息表，补齐“主业务成功但消息不丢”的发布可靠性闭环
- 延迟消息体系（用于预约提醒、超时取消、延迟补偿等真实场景）
- 真实统计 / 预警类下游消费者
  - 销售日报或经营统计读模型
  - 库存预警与审计类消费者
  - 对账与补偿辅助消费者
- 单据状态机进一步完善
- 如果后面出现明确的系统配置 / 字典中心，也在这一轮再决定是否做更系统的缓存策略

### 说明

- 这一轮才适合认真把 Redis 往“业务中间件”推进
- `PR13` 只承接 MQ 直接需要的轻量 Redis 支撑；业务级幂等、防重、锁、热点保护统一留到这一轮
- `PR13.5` 已经补完库存原子更新、请求级幂等、缓存稳态和 MQ 发布确认；更重的发布可靠性闭环、延迟消息、真实下游消费者与热点库存专项治理统一留到这一轮
- 放在 MQ 之后更合理，因为这时业务边界和事件边界都已经更清楚

## PR19 Nacos / Gateway / 微服务前置评估

### 目标

只做评估，不急着上微服务。

### 内容

- 判断有没有必要拆
- 评估拆分对象、拆分边界、迁移成本和真实收益
- 判断是否真的需要 `Nacos`、`Gateway`、服务注册发现和配置中心

### 说明

- 模块化单体没有做好之前，不应该急着谈微服务
- 这一轮是技术评估，不是实施轮

## 总结

`PR11` 之后的推荐顺序如下：

1. `PR12` 模块化单体 + 轻量目录规范
2. `PR12.5` Redis 收口
3. `PR13` RabbitMQ 接入
4. `PR14` Docker / Ops / 部署整理
5. `PR15` 新前端全量迁移（已合并承接原 `PR15 ~ PR17`）
6. `PR18` 高并发与一致性增强
7. `PR19` 预约提醒延迟与聚合消息中心
8. `PR20` 代码审查、安全加固与消息隔离修复
9. 新分支 `microservices` Nacos / Gateway / 微服务前置评估
这条路线的核心原则是：

- 先稳业务模型，再稳模块边界
- 先把 Redis 用准，再把 MQ 用深
- 先把单体整理干净，再评估是否值得拆分

# 微服务前瞻备忘录

## 说明

本文档只用于记录 `PR12` 之后、更靠后的技术前瞻与候选方向。

这不是当前轮次的正式实施方案，也不代表项目会立刻进入微服务拆分。当前主线仍然是：

1. `PR12` 模块化单体
2. `PR12.5` Redis 收口
3. `PR13` RabbitMQ 接入
4. `PR14` Docker / Ops / 部署整理
5. `PR15` 之后再进入新前端迁移

只有当模块边界、缓存边界、异步事件和运行环境都稳定后，才适合认真评估是否继续向微服务演进。

## 当前判断

### 1. 微服务是后续学习目标，不是当前最优落地形态

Jasmine 当前仍然更适合先保持为模块化单体。

原因很明确：

- `PR11` 才刚完成业务模型重构
- `PR12` 还要继续收口域边界和跨域依赖
- `sales` 与 `inventory`、`vip` 与 `appointment` 之间仍有明显一致性耦合
- 如果现在直接拆服务，会过早引入最终一致性、幂等、补偿、调用链等复杂度

### 2. 未来可以明确朝国内企业风格微服务主线演进

如果项目后面真的进入微服务阶段，当前可以预设的技术主线是：

- `Spring Boot 3.5.x`
- `Spring Cloud 2025.0.x`
- `Spring Cloud Alibaba 2025.0.0.0`
- `Nacos`
- `Spring Cloud Gateway`
- `OpenFeign`
- `RabbitMQ`

其中 `Spring Cloud Alibaba 2025.0.0.0` 已经对应：

- `Spring Cloud 2025.0.0`
- `Spring Boot 3.5.0`

这意味着 Jasmine 当前使用的 `Spring Boot 3.5.x` 技术线，在未来进入微服务阶段时，已经具备可对齐的官方版本组合。

## 不建议现在直接做的事

以下内容暂不建议在当前阶段推进：

- 直接把现有模块一口气拆成多个独立服务
- 立即引入 `Nacos + Gateway + Sentinel + Seata + MQ` 全家桶
- 在边界还没收口之前就把 `sales` 与 `inventory` 强行拆成两个服务
- 为了“像微服务”而先做跨服务调用

这些动作会让系统复杂度快速上升，但不会立刻带来足够的工程收益。

## 未来候选架构形态

### 方案 A：更稳的拆分方式

适合真正要落地、同时希望复杂度可控的演进方式：

- `iam-service`
- `product-service`
- `trade-service`
- `crm-service`

对应职责：

- `iam-service`
  - 登录认证
  - 用户
  - 角色
  - 菜单
  - JWT
  - RBAC
- `product-service`
  - 花卉主数据
- `trade-service`
  - 销售
  - 库存
  - 交易统计
- `crm-service`
  - 会员
  - 预约

这套拆法更符合一致性边界，特别是：

- `sales + inventory` 高度耦合，先放在同一个交易域更稳
- `vip + appointment` 业务关系紧密，先放在同一个客户域更自然

### 方案 B：更偏学习型的拆分方式

如果后面主要目标是系统性练习微服务拆分、注册发现、网关转发、服务间通信，也可以采用更细粒度的学习型拆法：

- `iam-service`
- `flower-service`
- `inventory-service`
- `sales-service`
- `vip-service`
- `appointment-service`

这套方案的优点是知识点覆盖更广，但也会更早碰到这些问题：

- 跨服务一致性
- 库存扣减补偿
- 会员关联远程查询
- 幂等与重复消费
- 服务间链路追踪

因此它更适合后期学习和实验，不是当前首选。

## 关于 `jasmine-core`

不建议未来长期保留一个职责模糊的 `jasmine-core` 作为“大核心系统”。

原因是它很容易演变成“上帝服务”，把这些内容全部塞进去：

- 鉴权
- 用户权限
- 公共查询
- 基础配置
- 平台逻辑
- 各业务共享能力

更稳的做法是：

- 当前阶段：在模块化单体里明确 `iam` 域
- 未来阶段：如果要拆，直接把 `iam` 演进为清晰的 `iam-service`

## 未来技术演进建议顺序

如果后面真的要从模块化单体走向微服务，建议顺序如下：

1. 完成 `PR12`，把域边界和代码组织收口
2. 完成 `PR12.5`，把 Redis 使用边界理顺
3. 完成 `PR13`，先掌握 RabbitMQ 的异步事件模式
4. 完成 `PR14`，把运行环境和中间件编排整理稳定
5. 完成 `PR15` 到 `PR17`，让前后端都进入更现代、可维护的基线
6. 最后在 `PR18` / `PR19` 再认真评估微服务拆分

## 第一批建议接入的微服务组件

如果将来进入微服务阶段，第一批最值得接入的是：

- `Nacos`
  - 注册中心
  - 配置中心
- `Spring Cloud Gateway`
  - 统一入口
  - 路由转发
  - JWT 统一处理
- `OpenFeign`
  - 服务间 HTTP 调用
- `RabbitMQ`
  - 异步通知
  - 审计异步化
  - 事件驱动

而这些组件更适合放在更后期：

- `Sentinel`
- `Seata`
- `Dubbo`
- 服务网格

## 当前结论

当前最合理的工程路线仍然是：

- 先把 Jasmine 做成边界清楚、结构稳定的模块化单体
- 再补 Redis 和 RabbitMQ 的工程能力
- 最后再把微服务当成下一阶段的正式议题

一句话：

微服务是 Jasmine 的后续演进方向之一，但不是当前 `PR12` 的交付目标。

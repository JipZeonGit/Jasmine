# 项目约束说明

## 目标

这份文档用于统一 `Jasmine` 项目在文档、编码、注释、Git 提交、GitHub PR 和术语使用上的基本约束，避免后续协作时出现风格漂移、中文乱码、提交信息混乱或术语中英混写的问题。

## 一、文档语言约定

### 1. 文档默认使用中文编写

- 项目内 `Markdown` 文档默认使用中文编写
- 包括但不限于：
  - 升级路线文档
  - 设计说明
  - 阶段总结
  - 排查手册
  - PR 说明

### 2. 无必要时不要把中文术语改成英文

- 修改文件时，如无必要，不要把原有中文术语替换成英文
- 例如不要把：
  - `交换机` 改成 `exchange`
  - `路由键` 改成 `routing key`
  - `死信队列` 改成 `dead letter queue`

如果某个英文名是协议字段、类名、配置项、代码常量或命令行参数的一部分，可以保留英文；但正文说明优先继续使用中文表达。

## 二、文本编码约定

### 1. 优先使用 UTF-8 无 BOM

- 新增文本文件时，优先使用 `UTF-8 without BOM`
- 修改已有文本文件时，也尽量保持为 `UTF-8 without BOM`

适用范围包括：

- `.md`
- `.java`
- `.yml`
- `.xml`
- `.sql`
- `.js`
- `.ts`
- `.vue`
- `.ps1`
- `.bat`

### 2. 这样做的原因

- 防止 PowerShell、Maven、Java、Git、IDE 或终端里出现中文乱码
- 降低 Windows 与 Linux / CI 环境之间的编码差异

## 三、后端代码注释约定

### 1. 后端接口或长难句逻辑需要适当补 `//` 注释

在编写后端接口、事务流程、消息发布链路、复杂判断或长难句代码时，需要适当补一定数量的 `//` 注释，帮助后续阅读。

### 2. 注释要求

- 注释优先解释“为什么这样做”或“这一段在干什么”
- 注释要简洁直接，避免空话
- 不需要每一行都写注释
- 不需要写“给变量赋值”这种没有信息量的注释

### 3. 优先补注释的场景

- 事务提交后发布消息
- MQ 消费重试与死信处理
- 幂等判断
- 复杂 SQL 或复杂查询装配
- 一段方法内有多个业务阶段切换

## 四、Git 提交约定

### 1. 本地提交与推送前遵循统一提交格式

Git commit 信息使用以下格式：

```text
<type>：中文描述
```

示例：

```text
feat：补齐 RabbitMQ 重试策略与行为测试
fix：修复 Redis 配置前缀导致的幂等回退问题
docs：补充 PR13 死信排查手册与契约文档
```

### 2. commit 类型清单

- `feat`：新功能、新特性
- `fix`：修改 bug
- `perf`：更改代码，以提高性能
- `refactor`：代码重构，在不影响代码内部行为、功能下的代码修改
- `docs`：文档修改
- `style`：代码格式修改，注意不是 CSS 修改
- `test`：测试用例新增、修改
- `build`：影响项目构建或依赖项修改
- `revert`：恢复上一次提交
- `ci`：持续集成相关文件修改
- `chore`：其他修改，不在上述类型中的修改
- `release`：发布新版本
- `workflow`：工作流相关文件修改

### 3. 提交说明要求

- 类型使用英文关键字
- 描述使用中文
- 描述要贴合本次改动，不要写空泛标题
- 不要混用多种风格，例如一半英文一半无意义缩写

## 五、GitHub Pull Request 约定

### 1. PR 标题使用中文

PR 标题整体使用中文描述，建议格式：

```text
PR13：完成 RabbitMQ 最终阶段收口
PR12：模块化单体重组（草稿）
PR11：重建花卉门店核心业务模型
```

### 2. PR 正文使用中文

PR 发起时，正文使用中文编写。

### 3. PR 正文推荐格式

参考当前项目已有 PR 风格，推荐正文结构如下：

```markdown
## 本轮内容

- xxx
- xxx
- xxx

## 验证

- xxx
- xxx
- xxx

## 当前状态

- xxx
- xxx

## 说明

- xxx
- xxx
```

如果是已经比较稳定、偏总结型的 PR，也可以使用：

```markdown
## 目标

xxx

## 本次改动

- xxx
- xxx
- xxx

## 验证

- xxx
- xxx

## 说明

- xxx
- xxx
```

### 4. PR 正文写法要求

- 用中文描述改动内容
- 先写本轮做了什么，再写如何验证
- 如果还有已知限制、草稿状态或后续计划，需要单独写在“当前状态”或“说明”中
- 不要把大量英文术语直接替换原有中文表达，除非是命令、类名、配置项或协议字段

## 六、术语与表达约定

### 1. 中文术语优先

正文说明中优先使用项目已经稳定使用的中文术语，例如：

- 交换机
- 队列
- 路由键
- 死信
- 幂等
- 预约
- 库存流水
- 销售事件

### 2. 什么时候可以保留英文

以下情况可以保留英文原文：

- 类名
- 方法名
- 配置项
- 环境变量
- 命令
- 消息路由键
- 提交类型关键字

例如：

- `RabbitMqTopologyConfig`
- `APP_MQ_ENABLED`
- `inventory.changed`
- `feat：中文描述`

## 七、推荐执行方式

后续协作时，建议默认按下面顺序执行：

1. 文档优先用中文写
2. 新文件优先保存为 `UTF-8 无 BOM`
3. 后端复杂逻辑补必要的 `//` 注释
4. commit 使用 `<type>：中文描述`
5. PR 标题与正文使用中文
6. 修改文档或代码说明时，尽量保持既有中文术语不被无意义英文化

## 八、PR 模板示例

下面这份可以直接复用：

```markdown
## 本轮内容

- 完成 xxx
- 补齐 xxx
- 修复 xxx

## 验证

- 本地编译通过
- 本地/联调验证 xxx
- 管理台或日志确认 xxx

## 当前状态

- 当前主链已可用
- 仍有 xxx 暂未纳入本轮

## 说明

- 本轮以 xxx 为主，不扩展 xxx
- 后续如继续推进，优先处理 xxx
```
